# 已完成任务树的增量迭代设计

日期：2026-10-12。状态：用户已批准，已按本设计实施 0.1.9；操作与验证边界见 `docs/task-tree-incremental-iterations.md`。

## 目的与范围

Harness 应支持同一目标的持续演进：用户追加相关功能时，保留 treeId，在新 revision 中追加分支；旧 revision、原生审批、执行事实和 Final Report 保持原样。Claude 继续承担需求讨论、规划、编写和验证，Harness 记录、检查依赖与证据，不把每次修改强制变成新树。

用户已确认的方向：先优化插件，再用计数器“命名快照”测试原树扩展。本次不实现快照功能，不修改真实计数器树，不配置 JEV，不提交或推送 Git；此前未提交的修复与无关文件必须保留。

## 设计时的基线事实（0.1.8）

- TaskTreeService.assertTreeMutable 拒绝 completed 树的所有规划修改；选择已完成树只会停用工作流。
- 归属候选可包含 completed 树，merge 可以选择它，但后续保存草稿会因完成态被拒绝。这不是一个可用的增量入口。
- 原生审批绑定精确 tree revision；旧审批不能批准新分支。
- Final Report 已按 treeId/revisionId 唯一，并有禁止修改、删除的约束，可保存不同修订的交付报告。
- task_nodes 与 workflow_states 是当前状态投影；规划 revision、Attempt、Evaluation、Gate、Trace、报告和身份修复审计具有独立历史。
- 局部精炼、兼容旧证据查询、验证失效及调度器已存在，应复用而不是另写一套执行引擎。
- 计数器在首次报告后已有标题和乘法功能的直接修改。它们有项目级 Trace，但未重新验证旧 Task Tree 节点；旧节点的 succeeded 不是当前代码仍满足验收的充分依据。

## 方案选择

三个可行方向：每次迭代新建关联树；同树新修订；新增项目总树并把各次交付挂成子树。

采用同树新修订。它直接满足追加分支的需求，又保留每次交付的历史边界；本期不增加项目总树、跨树合并或迭代分支并行管理。

## 1. 明确的增量入口

不能简单删除 completed 的不可修改检查。普通 save/patch/select 仍不能隐式重开已完成树。

使用现有归属流程：用户在原生问题或自由文本中选择 merge 到现有 completed 树，或明确要求在该树追加功能。一次归属决定登记目标及用户回答 Trace。重开只授权记录新规划，不授权编写项目代码；新规划仍需一次原生 Plan 批准。

现有 harness_create_task_tree_draft 在收到以下完整输入时调用独立的增量服务，而不是绕过普通保存检查：

- 已解析的 merge 归属，属于同一 Project 和发起 Session，指向目标 completed 树。
- 精确的 expectedTreeRevisionId、完整的增量规划文档，以及 idempotencyKey。
- 当前修订已有 completed Final Report；没有活动 Attempt、其他活动工作流或不安全的未决操作。

先讨论，再提交一次完整规划。本期不提供先把树改成 draft、稍后再补计划的空重开操作，也不自动重开真实数据。

归属候选应标明 completed 树可用于增量迭代，不能把选择 merge 表述为重复执行旧交付。无需让用户同时批准“重开”和“代码执行”两份相同规划；归属登记与一次原生执行审批各自承担不同职责。

## 2. 本期支持的结构变化

采用追加型迭代：保留原根节点和所有旧节点 ID、旧分支；在根下新增一个或多个功能分支，可声明对既有节点、文件或契约的依赖。

- 旧节点正文和验收要求保持不变，根的 children 增加新分支。新增需求、约束记在新分支和规划上下文中。
- 旧关系与产物声明保留；可以新增关系和关联，也可为原契约增加新消费方，但不能悄悄更改既有接口签名或旧节点的责任。
- 新分支可以修改旧文件。这属于执行影响，不等于允许覆写历史规划；必须重新验证实际受影响的旧能力。
- 删除旧分支、重定义原目标、迁移旧节点责任、替换旧契约等超出追加边界的输入，本期明确拒绝，保持原树完成态；不静默退化成新建树。
- 没有结构增量的重复文档不产生新迭代。小修改继续走 direct execution，不因为此能力而强制建树或重开树。

## 3. 原子性、身份与历史

增量服务在一个事务内完成：复核归属与当前 revision、规划合法性和追加边界，生成新 revision，登记不可变迭代审计，更新当前状态投影，重新激活该树的规划工作流。

新增迭代记录关联：projectId、treeId、上一份报告、基础 revision、新 revision、归属回答 Trace、输入哈希、影响与复用决策、创建时间。相同 idempotencyKey 与相同输入返回同一结果；不同输入、过期 revision、跨项目、活动 Attempt 均拒绝且无部分写入。

- treeId 不变，revision 单调增加，workflow revision 也单调增加，不从 1 重置。
- 已有规范节点身份与 0.1.7 身份投影视图继续生效，包括已恢复的计数器根节点；不回写旧原始 JSON、节点修订或身份投影。
- 旧 Final Report 与已消费的原生审批不修改、不删除，不把历史失败 Gate 改成成功。
- 新修订必须有自己的审批、根验收与新报告。旧幂等键不能被误用为新版报告；查询明确区分当前修订报告和历史报告。
- 已归档树不能直接重开，必须先由用户明确恢复；仅查询、选择已完成树或说“继续”不会重开。

## 4. 证据复用与新鲜度

确认过的需求范围与验证成功是两类事实。未变的旧规划确认可继承，但旧成功证据必须经过可复用检查：

1. 节点正文及 taskNodeEvidenceContext 与来源修订兼容。
2. 成功 Evaluation/Attempt 的证据完整，没有适用于当前迭代的失效记录。
3. 关联文件、契约、环境及依赖的验证基线可核对且没有改变。

在新版交付时保存不可变的产物指纹清单，以便下一次迭代核对。项目内可读取的关联文件使用内容哈希；契约使用签名/版本。不存在、不可读取、超出项目范围或不能确定验证时内容的产物记为 unknown，不能用修改时间或当前 succeeded 替代证明。指纹数据记录在报告关联的历史清单中，不改写报告或旧 Artifact 历史。

旧版本报告没有指纹时不补造基线：将相关证据判为需重新验证。已记录的交付后 Edit/Write 和契约变更作为确定的影响输入；未记录的当前文件变化通过内容基线比较发现。

影响从新分支计划修改的产物、交付后的实际变更和不确定基线出发，经产物/契约关联、depends_on 及验收祖先传播；通信边不无条件扩散失效。旧成功事实仍保留，只改变新修订的复用资格与当前投影。

结果分三类：新增节点需要实施；受影响/无法证明有效的旧节点需要补验；可证明未受影响的旧节点复用证据。补验优先跑验证，不要求重写既有实现；失败后才在新规划授权范围内修复。首次对缺少基线的老树迭代可能需要较多补验，这是安全回退，不是无条件重跑全树。

根节点永远重新验收，因为整体交付范围已经增加。新版根验收不能引用旧根 Gate 作为新版整体通过依据。

## 5. 工作流衔接

新修订进入 task_tree_refinement/branch_confirmation，沿用 readiness、原生 Plan 审批、skeleton_pass、分支执行/验证、root_verification、final_report。

- 未受影响的旧确认及 verified 分支在新修订中建立有来源的复用投影；不是伪造新的成功 Attempt 或 Gate。
- 新增或受影响节点保持待确认/待执行/需补验状态。旧根必须重新确认新增范围并重新验证。
- 骨架门在新修订核对全局条件，但复用经过检查的旧骨架事实，只要求新增或受影响骨架运行。
- 分支状态初始化和调度不得把有效旧分支全部重置 pending，也不得把已失效旧分支直接复制为 verified。
- 旧节点兼容证据查询、局部恢复与新报告聚合使用相同复用规则，不能出现调度认为成功但最终报告拒绝的口径差异。
- 每次原生审批只批准当前修订。上一轮 profile 的 completed 收尾不影响新迭代，旧会话恢复也不能绕过新审批。
- 完成新版后按现有设计停用工作流；裸“继续”仍正常结束，小修改仍可直接执行。

## 6. 对外与存储边界

新增迭代服务及纯追加/复用分析单元，接入现有 draft/affiliation、工作流、验证与最终报告服务。MCP 继续使用已有归属及 create-draft 路径，返回本次增量的基础报告、新 revision、复用/补验/新增节点摘要。查询提供报告历史与当前迭代信息。

数据库采用新增表/索引保存不可变迭代审计和报告关联指纹，不批量重写现有报告或历史，不在升级时自动重开树。CLI 如需提供诊断入口也不能绕过同一授权与 revision 检查。

现有 Runtime 原生引导须保持：小需求不强制归属；availableActions 不是全部项目权限；pause 只暂停当前请求；直接执行保留 Trace；明确结构化请求的门禁不放宽。

## 7. 验收

实现使用临时 SQLite 及项目 fixture，先观看失败测试，再实现，独立审查并运行 npm run check。至少覆盖：

- 真正完成的一棵树追加一个独立分支，同 treeId、新 revision，旧报告及所有原始历史字节不变；可复用旧分支不重跑，新分支及新根完整执行并产生第二份报告。
- 新分支修改旧文件，影响旧能力验证；直接执行的交付后变更不会被漏掉。
- 契约/依赖变更、文件内容变化但 mtime 不变、缺少旧指纹、不可读取/越界文件，均不能误复用证据。
- 暂停、空“继续”、查询、选择 completed 树均不重开；已归档树、跨项目、错误回答 Trace、其他活动工作流、活动 Attempt、过期 revision、无增量和不支持结构变化均拒绝。
- 整个增量提交的幂等性、失败回滚与重启续接；用户只作一次本轮原生 Plan 批准。
- 原审批不能批准新增代码；旧报告幂等键不能完成新迭代；当前查询不能拿旧报告声称新版已完成。
- 复用分支的调度、骨架门、验证失效与报告汇总一致；0.1.6 局部恢复、0.1.7 身份隔离和 0.1.8 原生引导全量回归。

插件升级不等于真实项目恢复。本能力实现并通过自动化检查后，才由用户在计数器提出命名快照需求，选择合并原树，验证从讨论、追加规划、一次原生审批到新版最终报告的实际 Agent 闭环。
